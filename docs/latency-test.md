# Test log

## 2026-11-09 — KDSP server & protocol parse verification (PC, localhost)

Environment: Linux, Python 3.12, FFmpeg 8.1.2. Sample generated by
`server/generate_sample.sh` (testsrc2, 1280x720@25, H.264 with AUDs,
GOP 50). Verified with `server/test_parse.py`, which implements the
receiver rules from `protocol.md`.

| Test | Result |
|---|---|
| Access-unit splitting of the sample | 3,000 AUs from the 120 s sample (= 25 fps × 120 s) — as expected |
| Frame parse, 75 frames, clean stream | OK — headers valid, payloads start with Annex B start codes, 2 keyframes in 75 frames (GOP 50) — as expected |
| Sender→receiver timestamp delta (localhost) | min 0 ms, max 3 ms |
| Weak-network mode `--drop 0.3`, 40 frames | OK — sequence gaps detected and reported per gap; parsing continued without desync |

Notes:
- These are **protocol/server** results on one machine, not Android
  playback latency. Player-side latency numbers go here only after the
  custom ijkplayer build plays the stream on a real device.
- First implementation pitfall found and fixed during this test: a
  byte-by-byte Python scan for start codes over a 60 MB stream is too
  slow; the splitter now uses a regex scan (~0.5 s for the full sample).

## 2026-11-09 — Protocol renamed KPLD → KDSP

At the owner's request the fictional protocol was renamed from KPLD to
**KDSP (Device Streaming Protocol)** for a more professional presentation.
The rename covers the URL scheme (`kdsp://`), the frame magic
(`0x4B445350`, ASCII `KDSP`), file names (`server/kdsp_server.py`), the
Android package (`demo.kdsp.player`) and all documentation. Re-verified
after the rename: server + `test_parse.py`, 60 frames parsed OK,
2 keyframes, timestamp delta 0–1 ms on localhost.
